# AgentHub 协作 DAG 升级设计稿

> 目标：把 AgentHub 的多 Agent 协作从“能分发任务”升级为“可编排、可审查、可追踪、可纠偏、可向领导汇报”的完整 DAG 工作流。

## 背景

当前 AgentHub 已经具备多 Agent 协作的基础能力：

- 有 `dispatch plan`，能把任务拆成若干子任务。
- 有 `AgentRunner`，能运行单个 agent / 子任务。
- 有 `task_result_report`，能让任务执行结果结构化回传。
- 有 `sub-agent manager`，具备子 agent 创建、恢复、列出、等待等雏形能力。
- UI 侧已经有群聊、Orchestrator、任务卡与部分协作状态展示。

但现阶段仍然存在明显缺口：

- 任务分发后，分发者没有持续监听进度。
- 子任务完成后，没有稳定、统一的领导摘要。
- 代码质量、结构、美观度缺少系统化审查。
- 子 agent 的产出缺少“重写 / 返工 / 接手修正”的闭环。
- 用户希望减少频繁权限确认，尤其是同一会话内的重复审批。

因此本设计的目标不是“再加几个按钮”，而是把协作模式升级成一个真正的 DAG 工作流。

## 设计目标

1. **任务可编排**
   - 一个高层任务可拆成多个节点。
   - 节点支持依赖、并行、串行、重试、阻塞。

2. **子 agent 可自治**
   - 群聊中的每个 agent 可以管理自己生成的子 agent。
   - 但要受父节点约束，避免无限制扩散。

3. **Orchestrator 具备全局审查能力**
   - 能识别结构问题、审美问题、职责混乱、重复实现、接口不一致。
   - 发现问题后可要求群聊 agent 重写，而不是直接交给用户。

4. **分发者持续监听进度**
   - 任务不是发出去就结束。
   - 需要自动订阅状态变化、阻塞、完成、失败、等待确认等事件。

5. **领导汇报一体化**
   - 用户只接收面向领导的摘要，不被碎片化子任务刷屏。
   - 关键风险和需要拍板的点要明确升级。

6. **权限更顺滑**
   - 支持“当前会话权限全开”。
   - 同一会话内的重复权限请求不再频繁打断协作。

## 非目标

- 不追求一次性实现完整通用工作流引擎所有能力。
- 不把 AgentHub 变成独立的企业级 BPM 系统。
- 不强行让所有 agent 都能无限制创建子 agent。
- 不让 Orchestrator 自己直接改所有代码；它主要负责审查、协调、升级。

## 关键概念

### 1. DAG 节点

节点表示一个可执行单元，可能是：

- 需求理解
- 架构设计
- 前端实现
- 后端实现
- 测试验证
- 代码审查
- 文档整理
- 返工修正

每个节点都需要至少具备：

- `id`
- `agentId`
- `task`
- `taskKind`
- `dependsOn`
- `expectedOutputs`
- `acceptanceCriteria`
- `requiredEvidence`
- `status`

### 2. 任务执行实体

任务不只是消息，而是结构化执行对象。

执行实体需要记录：

- 谁发起
- 谁负责
- 依赖谁
- 输入是什么
- 输出是什么
- 是否已验收
- 是否阻塞
- 是否需要重试
- 是否需要升级给用户

### 3. 父子协作链

本方案采用层级化树状 DAG：

- 用户是最高领导层。
- Orchestrator 负责顶层任务拆分、总审查和总收口。
- 群聊 agent 负责自己分支内的执行与纠错。
- 子 agent 负责局部执行。

原则：

- 父节点可以创建、停止、重试、审查自己的子节点。
- 子节点结果必须先回到父节点。
- 不允许跨树乱接任务。

## 总体架构

### 角色分工

#### 用户

- 发起高层目标。
- 决定是否批准危险操作。
- 只接收摘要、风险、关键分歧和最终结论。

#### Orchestrator

- 将目标拆成 DAG。
- 分配负责人。
- 监听所有分支状态。
- 做全局审查：结构、审美、一致性、完成度。
- 必要时要求群聊 agent 重写。
- 最终向用户汇报。

#### 群聊 agent

- 负责一个任务分支。
- 可在自己的分支内创建子 agent。
- 需要监听子 agent 进度并收口。
- 需要审查下属产物，必要时重写或返工。

#### 子 agent

- 执行局部任务。
- 产出代码、文档、测试结果或设计结果。
- 不直接向用户汇报。

## 流程设计

### 1. 任务进入

用户提交一个任务，例如：

- 做一个前端页面
- 完成后端接口
- 优化某个模块结构
- 修复一个跨前后端问题

Orchestrator 先判断任务复杂度：

- 简单任务：可直接单节点执行。
- 中等任务：拆成 2~5 个节点。
- 复杂任务：拆成多层 DAG，并允许分支下沉给群聊 agent 和子 agent。

### 2. DAG 拆分

Orchestrator 生成一个初始 DAG，至少包含：

- 目标理解节点
- 方案节点
- 实现节点
- 验证节点
- 复审节点
- 汇报节点

拆分时要显式记录：

- 依赖关系
- 并行关系
- 负责人
- 交付物
- 验收标准

### 3. 分发与自治

群聊 agent 收到自己的分支后，可以继续拆子任务：

- 例如前端 agent 再拆列表、表单、状态管理、样式收口。
- 例如后端 agent 再拆 schema、接口、鉴权、错误处理。

规则：

- 只允许在自己的子树内扩展。
- 任何新增子节点都必须有父节点知道。
- 父节点必须对新增节点负责。

### 4. 进度监听

每个父节点都要持续监听子节点状态变化：

- `pending`
- `running`
- `blocked`
- `waiting_review`
- `waiting_input`
- `retrying`
- `complete`
- `failed`
- `aborted`

监听到状态变化后，父节点要更新自己的视图，并在需要时向上汇报。

### 5. 纠错与重写

父群聊 agent 和 Orchestrator 都具备纠错权：

- 结构不好：要求重写。
- 代码过散：要求重构。
- 命名混乱：要求统一。
- 逻辑有漏洞：要求补测或重写。
- UI 不够完整：要求重新收口。

纠错优先级：

1. 让原子子 agent 重写局部。
2. 让负责该分支的群聊 agent 亲自修正。
3. Orchestrator 升级问题给用户。

### 6. 汇报路径

汇报要分层：

- 子 agent → 父群聊 agent
- 群聊 agent → Orchestrator
- Orchestrator → 用户

每一层的汇报内容不同：

- 子 agent：事实和产物。
- 群聊 agent：是否满足局部目标，哪里还要修。
- Orchestrator：全局状态、主要风险、是否建议继续、是否需要用户决策。

## Orchestrator 全局审查能力

Orchestrator 不只是调度器，还要是总审查官。它的审查维度如下：

### 1. 结构审查

判断代码/任务结构是否合理：

- 责任是否单一。
- 文件是否过大。
- 模块边界是否清晰。
- 前后端接口是否对齐。
- 任务拆分是否符合依赖关系。

### 2. 审美审查

这里的“审美”不是主观随意打分，而是可执行的产品级标准：

- UI 层级是否清晰。
- 交互是否顺手。
- 信息是否成组。
- 风格是否统一。
- 输出是否像一个完整产品，而不是拼接物。

### 3. 一致性审查

判断：

- 命名是否一致。
- 状态流转是否一致。
- API 约定是否一致。
- 错误处理是否一致。
- 汇报格式是否一致。

### 4. 决策审查

Orchestrator 发现问题后，有三种动作：

- 标记 `needs_rewrite`
- 要求某个群聊 agent 重写
- 将问题升级给用户决策

## 权限设计

### 当前会话全开

用户可以开启当前会话内的权限全开模式。

效果：

- 本会话中的 agent 不再频繁请求同类权限。
- 高风险操作仍可保留显式确认。
- 会话结束后状态默认可重置。

### 权限分级

建议至少分三类：

- **自动放行**：低风险、重复性强的操作。
- **会话级放行**：当前会话内默认通过。
- **强确认**：危险操作或系统级变更仍要问用户。

### 审批反馈

当权限请求出现时，应允许：

- 允许一次。
- 当前会话全开。
- 永久拒绝同类请求。
- 暂停当前协作。

## 状态模型

每个 DAG 节点建议使用以下状态：

- `pending`
- `running`
- `blocked`
- `waiting_review`
- `waiting_input`
- `retrying`
- `complete`
- `failed`
- `aborted`
- `needs_rewrite`

### 状态流转原则

- `pending` → `running`
- `running` → `complete | failed | blocked | waiting_review | needs_rewrite`
- `failed` → `retrying | aborted`
- `blocked` → `waiting_input | retrying | aborted`
- `needs_rewrite` → `running`

## 任务结果格式

任务结果必须结构化，至少包括：

- 结果摘要
- 完成状态
- 验收结果
- 变更文件
- 运行命令
- 测试结果
- 阻塞项
- 是否建议重写

Orchestrator 汇报给用户时，不直接贴原始日志，而是输出领导摘要：

- 做了什么
- 做得怎么样
- 哪些地方有风险
- 是否可以继续
- 是否需要用户拍板

## 群聊 agent 与子 agent 的关系

群聊 agent 应该具备：

- 创建子 agent 的能力。
- 审查子 agent 结果的能力。
- 要求子 agent 重做的能力。
- 必要时亲自接手修正的能力。

但它不应该：

- 脱离父节点约束无限创建子 agent。
- 直接绕过 Orchestrator 向用户宣布完成。
- 把未审查的结果当成最终结果。

## 推荐的实现顺序

为了避免一次性把系统做得过重，建议按这个顺序落地：

1. **权限全开（当前会话级）**
2. **任务 DAG 的结构化状态模型**
3. **Orchestrator 进度监听与领导摘要**
4. **群聊 agent 纠错与重写闭环**
5. **子 agent 自治与父节点约束**
6. **更完整的 DAG 调度与恢复能力**

## 风险与对策

### 风险 1：系统过度复杂

**对策**：先做受控 DAG，不要一开始就做通用工作流引擎。

### 风险 2：子 agent 乱生

**对策**：只允许在父节点控制下创建子 agent。

### 风险 3：Orchestrator 变成转发器

**对策**：强制加入全局审查职责与重写权。

### 风险 4：用户被权限请求打断

**对策**：当前会话全开 + 风险分级 + 紧急暂停。

### 风险 5：输出质量不稳定

**对策**：每个节点都要有验收标准和结果证据。

## 验收标准

当这套协作 DAG 设计落地后，至少应满足：

- 一个复杂任务能被拆成结构清晰的 DAG。
- 每个节点都有明确负责人和依赖。
- 父节点能看到子节点进度。
- 群聊 agent 能纠正子 agent 的错误。
- Orchestrator 能发现结构/审美/一致性问题并要求重写。
- 用户能开启当前会话全开，减少重复权限确认。
- 最终用户收到的是领导摘要，而不是碎片化中间态。

## 结论

AgentHub 的协作模式不应该停留在“发任务给 agent”。

它应该升级成：

- **任务可编排**
- **进度可追踪**
- **错误可纠偏**
- **子树可自治**
- **Orchestrator 可全局审查**
- **用户只看最终汇报**

这份设计的核心不是更复杂，而是**让复杂协作变得有秩序**。

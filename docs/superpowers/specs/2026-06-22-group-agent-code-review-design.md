# AgentHub 群聊全员代码审查设计
> 目标：把“代码差不差”交给群聊 agent 全员审查，Orchestrator 只负责总体方向、任务分派和最终收口，不下场做细节 code review。

## 背景
当前 AgentHub 已经具备多 Agent 协作的底座：
- `dispatch plan` 可以把高层目标拆成可执行任务。
- `AgentRunner` 可以执行单个 agent 或子任务。
- `report_task_result` 已经能把任务最终结果结构化回传。
- `report_task_progress` 已经能把执行中的进度结构化回传。
- `pendingDispatchPlans` 已经支持计划审批、拒绝、修改这类“计划层审查”。

但这套能力还不等于“代码审查”。目前缺少的是：
- 由群聊里的其他 agent 组成审查面，而不是让 Orchestrator 自己去看代码细节。
- 对代码变更做结构化、可汇总、可驱动重写的审查结果。
- 一条明确的闭环：代码完成 → 全员审查 → 汇总结论 → 必要时重写。

用户已经明确了职责边界：
- **群聊 agent 查代码。**
- **Orchestrator 不参与细节审查。**
- **Orchestrator 只把握总体方向。**

所以这份设计只解决一件事：把“查代码”从 Orchestrator 手里移出去，交给群聊 agent 集体完成。

## 设计目标
1. **所有群聊 agent 都参与审查**
   - 只要是本会话里的群聊成员，都应参与代码审查。
   - 原作者不审自己的代码。

2. **审查结果结构化**
   - 每个审查 agent 输出统一格式的结论。
   - 结论必须能被系统聚合，而不是只靠自然语言读懂。

3. **Orchestrator 只看结论，不看代码细节**
   - Orchestrator 负责判断是否继续、是否重写、是否升级给用户。
   - 不要求 Orchestrator 对源码逐行给出点评。

4. **审查能驱动重写闭环**
   - 一旦审查发现结构、正确性、测试、可维护性问题，就能回流到 rewrite。
   - 让“写完”不等于“直接交付”。

5. **不破坏现有 DAG / 子 agent / 计划审批链路**
   - 计划审批仍然走现有 `pendingDispatchPlans`。
   - 代码审查是执行后的独立阶段，不替代计划审批。

## 非目标
- 不把 Orchestrator 做成代码审查员。
- 不引入通用 BPM 或企业工作流引擎。
- 不允许群聊 agent 脱离父节点无限自创审查树。
- 不让审查 agent 直接改写工作区；审查应优先是只读。
- 不在这一步重做进度汇报和阻塞链。

## 现状与缺口
### 已存在的能力
- `DispatchTaskKind` 里已经有 `review`，说明“审查任务”这个概念在类型层是允许的。
- `report_task_result` 已经能回传结构化完成结果。
- `pendingDispatchPlans` 已经能对“计划”做 approve / reject / revise。
- `TaskProgressReport` 已经能做执行中的状态更新。

### 仍然缺的能力
- 代码审查结果的专门契约。
- “所有非作者群聊 agent 都必须审”的 fan-out 规则。
- 审查结果的聚合与冲突裁决规则。
- 审查卡片 / 审查面板 / 审查摘要的 UI 呈现。
- rewrite 触发条件的统一判定。

## 方案对比
### 方案 A：复用 `report_task_result`
审查 agent 继续使用现有结果上报工具，只是在 `summary`、`blockers`、`acceptanceResults` 里表达审查意见。

**优点**
- 实现成本最低。
- 不需要新增工具或新 schema。
- 和现有任务结果链路保持一致。

**缺点**
- 语义不干净：实现结果和审查结果混在一起。
- 很难稳定区分“任务完成”与“审查通过”。
- 后续做聚合、统计、UI 展示时会越来越别扭。

### 方案 B：新增专用 `report_task_review`（推荐）
专门为代码审查建立一个结构化上报契约，审查 agent 只负责给出 review verdict 和 findings。

**优点**
- 语义清晰：实现结果与审查结果彻底分离。
- 便于聚合多个 agent 的审查意见。
- 便于 UI 呈现“谁审了、谁反对、谁建议重写”。
- 适合以后扩展成“代码审查 / 设计审查 / 文档审查”的统一模式。

**缺点**
- 需要新增 schema、工具和聚合逻辑。
- 初始实现比方案 A 稍重。

### 方案 C：纯聊天自然语言审查
审查 agent 直接在群聊里发文字评论，由 Orchestrator 或人眼自己读。

**优点**
- 最快上手。
- 没有新协议成本。

**缺点**
- 不可聚合。
- 不可统计。
- 很容易丢结论。
- 长远看会把群聊刷成“审查聊天群”，不是工作流。

**结论**：选 **方案 B**。

## 推荐设计
### 1. 角色边界
#### Orchestrator
- 负责把高层目标拆成 DAG。
- 负责把代码任务完成后的审查阶段发起给群聊 agent。
- 负责收集所有审查结果并做总体裁决。
- 负责把“需要重写”这件事分派给合适的 agent。
- **不负责逐段阅读源码，也不负责逐行挑 bug。**

#### 群聊 agent
- 负责对代码任务进行审查。
- 负责指出结构、正确性、测试、接口、风格、风险问题。
- 负责在必要时要求重写。
- 负责在自己的能力范围内给出可执行的修改建议。
- 允许读取 diff、产物、上下文和必要测试输出。
- 默认只读，不直接改工作区。

#### 原作者 agent
- 不审自己的代码。
- 如果审查结果要求重写，原作者优先接回 rewrite 任务。

#### 用户
- 只看最终的审查摘要、主要问题和是否继续。
- 不被一堆中间审查日志刷屏。

### 2. 触发条件
审查阶段只对**代码类任务**强制开启，至少覆盖：
- `taskKind: 'code'`
- 产出文件修改的任务
- 会影响运行结果、接口、结构、测试的任务

暂不把“普通文档整理”或“纯讨论任务”纳入强制代码审查。

### 3. 审查 fan-out
当一个代码任务完成后，系统自动生成一个审查包，并发给同一群聊里的所有非作者 agent。

审查包至少包含：
- 原始任务目标
- 验收标准
- 变更文件列表
- 相关 diff 或关键片段
- 相关测试结果
- 上下文摘要
- 该任务在 DAG 中的位置和依赖

所有审查任务并行执行，互不依赖。

### 4. 审查报告契约
建议新增专用结构化报告，例如 `TaskReviewReport`，由 `report_task_review` 上报。

建议字段：
- `verdict`: `pass | needs_changes | must_rewrite`
- `summary`: 一句话结论
- `findings`: 结构化问题列表
  - `severity`: `low | medium | high | critical`
  - `category`: `correctness | structure | api | test | style | risk | performance | security`
  - `subject`: 问题指向的文件、函数或模块
  - `detail`: 问题描述
  - `suggestion`: 建议如何修
- `filesReviewed`: 审查过的文件列表
- `commandsRun`: 运行过的只读验证命令（可选）
- `rewriteRequired`: 是否明确要求重写（可选，通常由 verdict 推导）

### 5. 聚合与裁决
Orchestrator 不自己判断代码好坏，只做聚合。

建议的裁决规则：
- **任一 reviewer 给出 `must_rewrite`**，且问题属于结构、正确性、接口错位或测试失败，即进入重写。
- **没有 `must_rewrite`，但存在多个 `needs_changes` 或中高严重级问题**，进入修改后再审。
- **所有 reviewer 都是 `pass`**，或只有低级别建议项，则通过。
- **审查结果冲突** 时，取最高严重度为准，并把冲突点写进摘要。

### 6. 重写回路
如果审查结论不是通过，系统应当：
1. 把所有 reviewer 的结构化意见合并成一份“重写包”。
2. 将重写任务派回原作者，或派给最适合重写的群聊 agent。
3. 保留原始审查记录，方便下一轮比对。
4. 重写后再次走同样的全员审查。

### 7. UI 呈现
审查不应该只停留在后台日志里，前端要看得见。

建议 UI 形态：
- 代码任务卡上显示“审查中 / 已通过 / 需重写”。
- 显示参与审查的 agent 头像或名字。
- 显示每个 reviewer 的 verdict chip。
- 点击后展开审查详情抽屉，看到：
  - 每个 agent 的结论
  - 关键问题
  - 严重级别
  - 是否建议重写
- Orchestrator 的总览区只显示汇总结论，不展示源码批注。

### 8. 权限与边界
- 审查 agent 默认只读，不写工作区。
- 审查阶段可以允许必要的只读验证命令，但不应默认赋予写权限。
- 如果某个 reviewer 需要更深入验证，可由系统单独授权，只在审查任务范围内生效。
- 审查 agent 不能跳过 Orchestrator 直接对用户宣布“已完成”。

## 失败与异常处理
### 1. 审查 agent 超时
- 记录为未完成审查，不把它当成通过。
- 如果大多数 reviewer 已完成，可先给出临时聚合结论，并标记“审查不完整”。
- 必要时再补一个备用 review 回合。

### 2. 审查 agent 缺席
- 如果群聊里有 agent 不可用，系统应明确标记缺席。
- 不要静默跳过而假装“全员审查”完成了。

### 3. 审查意见冲突
- 取最高严重级问题为裁决基准。
- 将冲突摘要写入总览。
- 不让 Orchestrator 以“主观感觉”直接压掉审查结果。

### 4. 原作者自审
- 默认禁止。
- 如果系统误把原作者也派入 review，必须自动剔除。

### 5. 单 agent 会话
- 如果当前群聊里只有一个 agent，无法形成“全员审查”。
- 这种情况要显式降级，并在 UI 上提示“缺少 peer reviewer”。

## 实施顺序
1. **先定义审查报告 schema**
   - 先把结构化输出契约定住。

2. **再做审查 fan-out**
   - 代码任务结束后，自动把审查包发给所有非作者 agent。

3. **再做聚合与裁决**
   - 把多份审查意见合并成一份最终结论。

4. **最后补 UI**
   - 让用户能看见谁审了、怎么判、为什么需要重写。

## 验收标准
这套设计落地后，至少要满足：
- 任意代码任务结束后，系统会自动发起群聊全员审查。
- 原作者不会审自己的代码。
- 每个审查 agent 都能输出结构化 verdict 和 findings。
- Orchestrator 能基于审查结果决定通过、修改或重写，但不需要阅读源码细节。
- 用户能在 UI 上看到汇总审查结果，而不是只有任务完成状态。
- 现有的计划审批链路不被破坏。

## 结论
这套协作模式应该变成：
- **任务拆分交给 Orchestrator**
- **代码审查交给群聊 agent 全员**
- **总体方向和最终收口交给 Orchestrator**

这样 AgentHub 就不会变成“Orchestrator 既要指挥又要亲自查代码”的混合怪物，而是一个分工明确、可审查、可重写的协作系统。
